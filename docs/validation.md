# Validation

OpenMC uses complementary validation levels to verify the source tree,
runtime integration, and publication-oriented experimental workflows.

The validation strategy distinguishes between portable checks that can be
executed on a development host, tests that verify the expected repository
structure, complete builds requiring the OpenMC FEC dependencies, and
integration or reproducibility workflows requiring the reference bLEO
environment.

## Portable checks

The standard portable validation is:

```bash
make clean
make check
```

`make check` compiles the portable traffic applications and performs Python
syntax validation for the monitoring, experiment orchestration, analysis,
and reproducibility scripts.

These checks do not require NFQUEUE, libfec, or lcrq and can therefore be
executed on development hosts that do not provide the complete OpenMC
runtime environment.

Shell scripts can additionally be checked using:

```bash
bash -n scripts/*.sh tests/*.sh tests/*/*.sh
```

## Test suite

The maintained test entry point is:

```bash
bash tests/run_tests.sh
```

The default test suite performs lightweight smoke checks. These verify that
the principal source, configuration, monitoring, and experiment files are
present and that the repository reports the expected OpenMC release version.

The smoke tests intentionally do not require the complete FEC build
environment and can therefore be executed independently of bLEO.

See `tests/README.md` for the detailed test-suite structure.

## Complete build validation

A complete OpenMC build requires the native runtime dependencies:

- NFQUEUE;
- libfec for Reed--Solomon coding;
- lcrq for RaptorQ coding.

Their availability can be checked with:

```bash
make check-dependencies
```

In an environment providing these dependencies, build all OpenMC
executables using:

```bash
make all
```

The reference Ubuntu/bLEO container environment provides the dependencies
used for the validated OpenMC deployment.

## bLEO integration baseline

When an operational bLEO deployment is available, the test suite can also
invoke the integration baseline:

```bash
bash tests/run_tests.sh --with-bleo
```

The same workflow can be started directly with:

```bash
sudo bash tests/baseline/run_baseline.sh
```

This test invokes the existing Phase 3.5 validation workflow and requires
the configured Docker containers, the complete OpenMC runtime dependencies,
and administrative privileges for the networking operations used by bLEO.

The underlying validator can also be executed directly:

```bash
sudo ./scripts/validate_phase3.5.sh
```

The Phase 3.5 workflow checks compatibility between legacy positional
arguments, explicit long-form arguments, and reusable runtime profiles for
both the Reed--Solomon and RaptorQ backends.

### Historical baseline criteria

The Phase 3.5 workflow was originally defined for the OpenMC v0.1.0
functional baseline. Its reference loss-free experiment expected:

```text
Generated datagrams     2000
Delivered datagrams     2000
Completed blocks         250
Decode failures            0
```

These fixed values should be interpreted as historical regression criteria,
not as the sole release-acceptance criteria for OpenMC v0.1.1.

OpenMC v0.1.1 introduces deadline-based traffic generation and additional
instrumentation for the reproducibility experiments. Under a strict
generation window, host scheduling or runtime timing can cause fewer
datagrams than the historical fixed target to be generated. In such a case,
the legacy Phase 3.5 validator can report a fixed-count mismatch even when
all datagrams actually generated by the source are successfully processed
and delivered.

For this reason, the bLEO baseline is retained as a useful integration,
compatibility, and regression check, while current experimental validity is
assessed by the campaign-specific validation implemented by the maintained
experiment and reproducibility workflows.

## Experimental validation

The maintained experiment runner performs functional validation for each
run and records the resulting values in the run manifest.

Depending on the campaign, the validation information includes quantities
such as:

- generated packets;
- packets intercepted by the OpenMC gateway;
- delivered packets;
- completed FEC blocks;
- decoding failures;
- source-to-gateway and end-to-end packet loss;
- delivery ratio;
- generation-rate or target-achievement ratio;
- experiment-window integrity.

The applicable criteria depend on the experimental campaign rather than on
a single repository-wide fixed packet count.

The experimental methodology and campaign-specific acceptance criteria are
documented in:

```text
reproducibility/experimental_protocol.md
```

## Instrumentation validation

The publication workflow also verifies that the resource and timing
instrumentation introduced for the experimental evaluation does not alter
OpenMC's functional result.

The validation procedure is documented in:

```text
reproducibility/validation/README.md
docs/experiment5-instrumentation-validation.md
```

In the reference bLEO environment it can be executed using:

```bash
sudo python3 reproducibility/validation/validate_instrumentation.py \
    --execute --force
```

The validation compares instrumented and functional-baseline executions for
both RaptorQ and Reed--Solomon. Packet delivery and FEC outcomes must remain
functionally equivalent; timing and resource measurements are not expected
to be identical.

## Publication-level reproducibility validation

Publication-facing experiments use additional validation and analysis tools
under `reproducibility/`.

These workflows validate experimental run manifests, aggregate the accepted
runs, regenerate publication results, and verify the provenance of frozen
publication artefacts.

For example, the analysis workflow includes:

```bash
python3 reproducibility/analysis/validate_runs.py --campaign fig2
```

Additional publication-specific procedures are documented in:

```text
reproducibility/analysis/README.md
reproducibility/experimental_protocol.md
```

Frozen raw and processed experimental data associated with the SoftwareX
evaluation are archived separately in the accompanying dataset in the UPCT
Digital Repository (https://doi.org/10.82432/10317/25392). The GitHub
repository contains the maintained software, experiment orchestration,
validation, and analysis tools.

## Release validation

A release should therefore not be accepted on the result of a single
validation script. OpenMC v0.1.1 uses the following complementary checks:

1. `make check` for portable compilation and Python syntax validation;
2. `bash tests/run_tests.sh` for repository smoke checks;
3. `make all` in an environment providing NFQUEUE, libfec, and lcrq;
4. the bLEO integration baseline when the reference deployment is available;
5. the campaign-specific experimental and reproducibility validation
   required for publication results.

The complete release procedure, including repository hygiene, metadata
verification, and publication checks, is documented in `docs/release.md`.
